# T11b quantisation quality — 2026-11-01

**Result: PASS for the KV-cache comparison.** `fp8_v4` reproduced the `fp8`
answers exactly on the retrieval harness, with a mean top-5 KL of 0.00017 nats.
`fp8_v4` is not adopted because plain `fp8` already admits 200k with `M = 1.0`.

## Method

Same `qwen3.8-27b-mxfp4.rad` container and flags, changing only
`--kv-cache-dtype fp8` → `fp8_v4`. Three retrieval prompts of ~6,381 tokens each
put a different access code at 10%, 50% and 90% depth. Requests were greedy
(`temperature: 0`), `reasoning_effort: none`, `max_tokens: 16`, with
`logprobs: true, top_logprobs: 5`.

The prompt text and tokenisation are identical between the two runs. The
comparison was done twice: through the engine's local API for the log-probs, and
through the authenticated edge in the automated test.

## Results

| Case | Depth | fp8 | fp8_v4 | Match |
|---|---|---|---|---|
| `ZX-9271` | 10% | correct | correct | exact |
| `QK-4418` | 50% | correct | correct | exact |
| `MV-3057` | 90% | correct | correct | exact |

| Metric | Value |
|---|---|
| Task accuracy | **3/3 fp8**, **3/3 fp8_v4** |
| Exact output matches | **3/3** |
| Token agreement | **22/22** |
| Mean top-5 KL (nats) | **0.00017** |
| Max top-5 KL (nats) | **0.002974** |
| fp8 KV pool | 6.25 GiB (6.10 GiB attention + state), 12,500 blocks |
| fp8_v4 KV pool | 4.91 GiB (4.77 GiB attention + state), 12,500 blocks |
| Peak VRAM (fp8 / fp8_v4) | 20.58 GiB / not separately sampled (same weights; smaller pool) |

The KL is computed over the union of the two top-5 distributions, with 1e-9
smoothing for mass outside the top-5; it is a task-level harness, not a
full-vocabulary KL. The exact-match result is the stronger signal here: changing
only the KV cache did not alter the generated tokens.

`fp8_v4` actually uses a **smaller** KV pool (V is int4), so it would increase
headroom. It was not adopted because `fp8` already passed E0 (`M = 1.0`) and the
baseline is the conservative choice.
