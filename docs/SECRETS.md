`run/ipa-data` is the realm: back up the whole directory (or `ipa-backup`) before
rotating or upgrading. `secrets/` is gitignored and must be backed up separately;
losing it does not lose the realm, but the admin/DM passwords must then be
recovered with the IPA recovery procedures.

## What the rotation scripts guarantee

All scripts source `scripts/lib.sh` and share these properties:

1. Secrets travel on **stdin**, never argv. The DM script additionally uses
   `ldapi://` with SASL EXTERNAL, so even the old password is not needed.
2. The new value is **verified** before it is written to `secrets/`.
3. Writes are in place: an atomic rename would leave a bind-mounted gateway on the
   old inode.
4. The gateway is recreated (not merely restarted) because `radiance` and the mock
   share its network namespace.
5. If the gateway no longer authenticates, the LDAP bind and API-key scripts roll
   back; the certificate script restores the previous key/cert pair.

## Caveats

- **Admin minimum lifetime.** FreeIPA's global policy sets `krbminpwdlife=3600`
  (1 hour). A second reset inside that window fails with *Too soon to change
  password*. `--force` sets `minlife=0` only for the reset and restores the
  previous value **before** destroying the ticket; the script now restores the
  policy while authenticated. Confirm with `ipa pwpolicy-show` afterwards.
- **Cached service tickets.** Keytab and certificate rotation invalidate cached
  service tickets. Run `pi-krb login` again; `pi --continue` then works with the
  new ticket. The shim reports `401 credentials expired` until then.
- **Old test-runner secrets.** Compose copies secrets at container creation. An
  already-running `test-runner` keeps the old admin password; the next
  `make test-fast` mounts the new one.
- **Certificate serials.** `rotate-cert.sh` revokes the previous serial with
  reason 4 (superseded) and shreds the previous private key after the new
  listener verifies. Certificates issued earlier for the same principal but a
  different key are harmless once the old key is gone; list them with
  `ipa cert-find --principal=HTTP/radiance.ipa.test`.
- **Revocation is not deletion.** The revoked certificate remains in the CA
  database and on the CRL. That is the intended audit trail.

## Scheduled keytab rotation

`deploy/systemd/` contains a user-service template. Install it for the account
that owns this checkout (that account must be able to run `docker compose`):

```sh
mkdir -p ~/.config/systemd/user
sed "s|@REPO_DIR@|$PWD|g" deploy/systemd/radiance-krb-rotate-keytab.service \
    > ~/.config/systemd/user/radiance-krb-rotate-keytab.service
cp deploy/systemd/radiance-krb-rotate-keytab.timer ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now radiance-krb-rotate-keytab.timer
systemctl --user list-timers radiance-krb-rotate-keytab.timer
```

The timer runs weekly at 04:17 with a randomized delay. It rotates the keytab
only; TLS certificates are valid for two years and are rotated manually with
`rotate-cert.sh`. Rotating the keytab logs out existing sessions' cached service
tickets, so schedule it outside working hours or accept one re-login.

## Verification after any rotation

```sh
docker compose --env-file .env ps
docker compose --env-file .env exec radiance-gateway \
    stat -c '%a %U:%G %n' /run/gateway/radiance.keytab
make test-fast
docker compose --profile client run --rm pi-login pi-krb status
```

The rotation scripts already run an authenticated `/v1/models` request when the
host has `kinit` and `curl`; the output says when that check was skipped.
